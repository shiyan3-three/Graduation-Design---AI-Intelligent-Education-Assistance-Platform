## 修复：ProtectedRoute 验证、网络异常兜底、JWT_SECRET 安全收紧 (gemini agent written)

### 做了什么
- **新增 `GET /api/auth/me` 接口**（`backend/routers/auth.py`）：使用 `get_current_user_id` 鉴权依赖，token 有效返回当前用户 profile（200），token 无效/过期触发统一 401，为前端提供轻量验证接口。
- **AppLayout mount 时后台验证 token**（`frontend/src/components/Layout/AppLayout.jsx`）：挂载后通过 `useEffect` 调 `GET /api/auth/me`，伪造/过期 token 被拒绝时，`requestJson` 全局 401 处理器自动 `clearAuthSession()` + 重定向；网络异常 fail-open，不误踢合法用户。
- **AuthPage 网络异常兜底**（`frontend/src/pages/AuthPage.jsx`）：`handleLoginSubmit` 与 `handleRegisterSubmit` 分别加 `try/catch`，`fetch` 抛出 / 代理失败时显示"无法连接后端服务，请确认后端已启动"，消除未处理 Promise rejection。
- **JWT_SECRET 默认值安全收紧**：默认值从 14 字节 `'dev-secret-key'` 统一替换为 44 字节 `'dev-secret-key-change-this-before-deploying-prod'`（`backend/routers/auth.py` 与 `backend/dependencies/auth.py`），`InsecureKeyLengthWarning` 消除；新增 `.env.example` 加必要换用说明，提示生产部署时覆盖使用。
- **测试文件同步**：`test_sessions_api.py`、`test_chat_tools_api.py` 模块级 `_JWT_SECRET` 以及 `test_auth_integration.py` 的 setUp 补充 JWT_SECRET 设置，防止签发/验证 key 不匹配导致断言失败。

### 改动文件
- `backend/routers/auth.py` — 新增 `GET /api/auth/me`，JWT_SECRET 默认值拉长至 44 字节

- `backend/tests/test_auth_api.py` — 新增 3 条 `/api/auth/me` 测试 + `_make_token()` 辅助
- `backend/tests/test_auth_integration.py` — setUp/tearDown 补 JWT_SECRET 环境变量

- `backend/tests/test_chat_tools_api.py` — `_JWT_SECRET` 回退值对齐

### 关键决策
- ProtectedRoute 保持同步检验 token 字面（无 token 直接挡），AppLayout 异步验证有效性，职责分离。
- 选择 fail-open 策略（网络错误不踢出用户）。
- JWT_SECRET 收紧选方案 B（默认值拉长而非强制失败），引入 `.env.example` 明确标注勿用于生产。
- 所有测试文件 JWT key 统一到同一默认或通过 setUp 显式设置，根治 key 不匹配导致断言失败的脆弱性。

### 踩坑
