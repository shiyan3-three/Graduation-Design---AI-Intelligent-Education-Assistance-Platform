## 任务：遗留 Bug 追加修复（MCP 子进程未继承题库环境）

### 做了什么
- 定位到 `question_tool` 只有在 `/api/chat` 链路里才会错误回落到 `llm_generated`，而 direct call 正常命中本地题库。
- 确认根因是 `backend/services/mcp_client.py` 在拉起 `backend.mcp_server` 时没有显式传递父进程环境，导致 MCP 子进程拿不到 `APP_DB_PATH`，从而看不到运行时题库。
- 为此新增 `backend/tests/test_mcp_client.py`，锁定 `call_mcp_tool()` 会把父进程环境透传给 `StdioServerParameters(env=...)`。
- 修复后重启后端，并用真实 `/api/chat` 复测“给我出一道关于二次函数的题”，确认 `question_tool` 返回 `source=ceval`。

### 改动文件
- `backend/services/mcp_client.py` - 为 MCP stdio 子进程显式传递 `os.environ.copy()`
- `backend/tests/test_mcp_client.py` - 新增 MCP 环境透传回归测试

### 关键决策
- 不在 MCP server 端单独重复解析 `.env` 兜底这类症状性补丁，而是在 client 拉起子进程时把父进程环境完整透传，保证题库路径、LLM provider 和搜索 key 都与主后端一致。

### 遇到的问题
- `question_tool` direct call 与 `/api/chat` 表现不一致，容易让人误判成“本地命中逻辑仍然失效”；实际是两条链路使用的进程环境不同。

### 当前结果
- `backend.tests.test_mcp_client` 已通过。
- 真实 `/api/chat` 再次验证“给我出一道关于二次函数的题”后，`assistant_message.tools_used[0].tool_name = question_tool` 且内部 `source = ceval`。
